# ADR 004: Adopt MCP 2026-07-28 Spec

**Status:** Accepted  
**Date:** 2026-08-09  
**Deciders:** Engineering team  

## Context

Anthropic released the MCP 2026-07-28 spec, moving MCP to a **stateless core** with hardened OAuth 2.0 and a versioned extensions framework. Our existing MCP implementation was already stateless at the HTTP layer (REST endpoints, no in-memory sessions), but lacked:

1. **PKCE flow** — only client credentials were supported
2. **Token persistence** — OAuth tokens died on process restart
3. **Extension framework** — no MCP Apps or Tasks support

This ADR documents the upgrade to full 2026-07-28 compliance.

## What Changed

### 1. Auth Hardening (Phase 1 — implemented)

**New DB table:** `mcp_auth_tokens`

| Column | Type | Purpose |
|--------|------|---------|
| `id` | UUID | Primary key |
| `connection_id` | UUID (FK) | Links to `mcp_connections.id` |
| `access_token` | Text | OAuth access token |
| `token_type` | String(20) | Usually "Bearer" |
| `refresh_token` | Text | For token refresh |
| `expires_at` | DateTime(tz) | When token expires |
| `scope` | Text | Granted scopes |
| `created_at` | DateTime(tz) | Row creation time |

**New OAuth flows in `core/oauth.py`:**

- **Authorization Code + PKCE** — production-grade user-interactive auth
  - `PKCEChallenge` generates `code_verifier` + `code_challenge` (S256)
  - `create_authorization_url()` returns the URL to redirect users to
  - `exchange_code()` sends `code_verifier` with the token exchange
- **DB persistence** — tokens survive process restarts
  - `save_token_to_db()` — upserts token to `mcp_auth_tokens`
  - `load_token_from_db()` — loads persisted token, refreshes if expired

**New endpoints in `routers/mcp.py`:**

| Method | Path | Purpose |
|--------|------|---------|
| `GET` | `/mcp/connections/{id}/authorize` | Start PKCE flow, returns auth URL |
| `GET` | `/mcp/callback` | OAuth callback, exchanges code, persists token |
| `GET` | `/mcp/connections/{id}/token` | Check token status |

### 2. MCP Tasks (Phase 2 — planned)

Long-running job support via versioned extension:

| Endpoint | Purpose |
|----------|---------|
| `POST /mcp/tasks` | Create a task |
| `GET /mcp/tasks/{id}` | Get task status |
| `DELETE /mcp/tasks/{id}` | Cancel a task |

### 3. MCP Apps (Phase 3 — planned)

Interactive UI rendering in conversations via versioned extension:

| Endpoint | Purpose |
|----------|---------|
| `POST /mcp/apps` | Register an app |
| `GET /mcp/apps/{id}` | Get render spec |
| `POST /mcp/apps/{id}/interact` | Handle user interaction |

## OAuth Configuration

The `auth_config` JSON on `MCPConnection` now supports these keys:

```json
{
  "oauth_client_id": "your-client-id",
  "oauth_client_secret": "your-client-secret",
  "oauth_token_url": "https://provider.com/oauth/token",
  "oauth_authorize_url": "https://provider.com/oauth/authorize",
  "oauth_redirect_uri": "https://your-app.com/mcp/callback",
  "oauth_scopes": ["read", "write"]
}
```

| Key | Required | Purpose |
|-----|----------|---------|
| `oauth_client_id` | Yes | OAuth client ID |
| `oauth_client_secret` | Yes | OAuth client secret |
| `oauth_token_url` | Yes | Token endpoint URL |
| `oauth_authorize_url` | No | Enables PKCE flow when set |
| `oauth_redirect_uri` | No | Required for PKCE flow |
| `oauth_scopes` | No | Requested scopes |

## PKCE Flow

```
User clicks "Connect" in MCP UI
        │
        ▼
GET /mcp/connections/{id}/authorize
  → stores code_verifier in auth_config
  → returns authorization_url
        │
        ▼
User visits authorization_url
  → authenticates with provider
  → provider redirects to /mcp/callback
        │
        ▼
GET /mcp/callback?code=...&state=project_id:connection_id
  → exchanges code + code_verifier for token
  → persists token to mcp_auth_tokens
  → updates connection status to "connected"
```

## Token Lifecycle

1. **Creation** — tokens created via client credentials or PKCE flow
2. **Persistence** — saved to `mcp_auth_tokens` table
3. **Refresh** — `load_token_from_db()` auto-refreshes expired tokens if `refresh_token` exists
4. **Revocation** — deleting a connection cascades to delete its tokens

## Migration

Run `alembic upgrade head` to create the `mcp_auth_tokens` table:

```bash
cd apps/api
alembic upgrade head
```

## Backward Compatibility

- Existing `client_credentials` flows continue to work unchanged
- `create_oauth_client()` factory accepts both old and new `auth_config` formats
- No breaking changes to existing endpoints
